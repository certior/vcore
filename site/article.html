The lethal trifecta takes three steps

Agent security rules now forbid combinations over a session. A one-line change to such a policy can open an exfiltration path that no single request reveals. vcore checks policy changes for sessions of any length, and its checker is proved correct in Lean.

Pauline BourigaultCertiorSeptember 2026

Rules with memory

In June 2025 Simon Willison named the lethal trifecta: an agent that can read private data, is exposed to untrusted content, and can communicate externally can be made to leak that data by anyone who can put text in front of it. Meta’s Agents Rule of Two turned it into a design rule: within one session, combine at most two of untrusted input, sensitive data, and the ability to change state or communicate.

Neither rule is about a single tool call. Reading a customer file is fine. Opening a pull request is fine. Opening a pull request in a session that has read a customer file and a public issue is not. A policy that enforces this has to remember what the session has done.

vcore keeps that memory as tags. Requests are paths with the tool first; statements attach effects to path patterns:

{
  "permit": ["Read/**", "WebFetch/**",
             "mcp/github/get_issue", "mcp/github/create_pull_request"],
  "forbid": ["**/.env"],
  "label": {
    "Read/customers/**": "private",
    "mcp/github/get_issue": "untrusted"
  },
  "block": [
    { "on": "mcp/github/create_pull_request", "after": ["private", "untrusted"] }
  ]
}

A request runs if some permit covers it, no forbid covers it, and no block that covers it has all of its tags in the session. Running it adds the tags labelled on it. That is the whole language (reference).

A one-line change

Figure 1 comes from a policy for a coding agent that reads a repository, browses the web, and reads issues and opens pull requests through the GitHub MCP server. Someone decides the team’s issue tracker is internal and deletes one line, "mcp/github/get_issue": "untrusted". It is the assumption behind the GitHub MCP exploit, in which a planted public issue made agents leak private repositories.

Read the trace one request at a time. Reading an issue is allowed before and after the change, and so is reading production configuration. Opening a pull request is blocked in a session holding private and untrusted under both policies, and allowed in a session holding only private under both. No request changes its decision in any given context. A review that compares the two policies request by request, even one that considers every possible set of session tags, finds nothing. What changed is which contexts a session can reach.

The question

Call the policies before and after an edit old and new. The edit adds no behaviour if every sequence of requests that new lets run to completion, old lets run too: new refines old. vcore check old.json new.json decides this and prints a counterexample when it fails. vcore satisfies policy.json rule.json uses the same check to ask whether a policy already enforces a rule such as the Rule of Two.

Two things make the question look out of reach. Sessions have no length limit, so no amount of simulation covers them. And requests are paths, so there are infinitely many, and a test of the requests you thought of misses the one you did not. Each has its own answer.

Short sessions suffice

Tags only accumulate, and a request allowed with some tags stays allowed with fewer. Suppose a long session, run by both policies, ends in a request that new allows and old blocks because the session holds private and untrusted. Some request in the session added each tag. Keep those, drop the rest, and replay. Every kept request is still allowed, since it now runs with no more tags than before. At the end old still holds both tags, so it still blocks; new holds no more tags than before, so it still allows.

So a counterexample never needs more than k + 1 requests, where k is the largest number of tags in any block of the old policy. The bound is tight. For the trifecta rule k = 2, and some pairs of policies differ only on sessions of three requests, because no single request carries both tags.

This also settles how deep a bounded search has to look. Two steps, read then send, is the natural guess, and it is wrong for exactly the rules people now write. On random policy edits, a search of all two-request sessions missed of the escalations; every one needed three or four requests.

Finitely many requests suffice

Patterns compare whole segments: exactly (a/b), as a prefix (a/b/**) or as a suffix (**/a/b). A request is covered by the same patterns as its representative: its longest matching prefix literal, then a segment no pattern mentions, then its longest matching suffix literal. With the patterns Read/**, Read/secrets/** and **/.env there are representatives, and every request behaves like one of them:

The middle segment is what makes this true. Glue a prefix literal straight onto a suffix literal and the result can match a pattern that the original request does not. The mistake is easy to make and hard to find by testing. It was seeded on purpose into vcore’s independent Z3 checker, and random differential tests did not catch it. The same mistake in the Lean definitions makes a proof fail.

Together, the two observations give a decision procedure. Explore the pairs of tag sets both policies reach within k requests, using only representative requests, and at each pair look for a request new allows and old blocks. It terminates, it is exact, and when it finds something the path it followed is the counterexample.

Proved in Lean

The checker, the bound and the compiler behind the runtime are written in Lean 4 and proved against the definition of the language. The headline statements:

theorem refines_iff_escalation_eq_none {old new : Authority} :
    Refines new old ↔ escalation old new = none

theorem short_counterexample {old new : Authority} (h : ¬ Refines new old) :
    ∃ w, new.Accepts w ∧ ¬ old.Accepts w ∧ w.length ≤ old.width + 1

-- the trifecta rule: three requests are needed, and two never suffice
theorem no_shorter :
    ∀ w : List Path, w.length ≤ 2 → unguarded.Accepts w → trifecta.Accepts w

theorem compile_allows (a : Authority) (ctx : Ctx) (x : Path) :
    Index.allows (a.map compile) ctx x = a.allows ctx x

theorem delegate_refines (child : Policy) (a : Authority) (ha : a ≠ []) :
    Refines (child :: a) a

In words: the checker reports no counterexample exactly when the new policy refines the old one, for sessions of every length and every request. Counterexamples are short, and for the trifecta rule no shorter session exists, which Lean’s kernel checks by running the checker. The index the runtime evaluates decides exactly as the policy it was compiled from. And a sub-agent that runs under its own policy together with its parent’s can never do more than the parent.

A proof is only as good as the definitions it is about. Two things guard those. Contract theorems state each rule of the language in a few lines (a forbid overrides every permit; a request with a . or .. segment never runs; tags are never removed), so a reviewer can check the semantics without reading its definition. And a mutation study seeds plausible bugs into the definitions: a block that fires on one tag of its combination, a compiler that overwrites instead of merging, a search one step too shallow. break the build.

What it does not promise

  • That a policy is right. vcore compares policies and checks rules; it does not know what either was meant to allow.
  • That a tool call is described faithfully. A request is what an integration says a call touches. The Claude Code integration resolves file paths and symlinks, reduces URLs to host and path, and refuses shell commands with pipes or substitution, but a permitted shell command can still do what its arguments allow. That mapping is tested, not proved.
  • Anything about the model. Tags record what a session touched, not what the model did with it.
  • Declassification, approvals or budgets. Tags only accumulate. The bound depends on it.

Where the tool has to choose, it fails closed: an empty list of policies allows nothing, a request with an empty, . or .. segment is always denied, and the hook denies a call when it cannot read the policy. What is verified lists every layer.

# build the proofs and the vcore executable
git clone https://github.com/certior/vcore && cd vcore
lake build

# the case study from this page
cd examples/coding-agent
../../.lake/build/bin/vcore check policy.json trust-issues.json
../../.lake/build/bin/vcore satisfies policy.json rule-of-two.json

For enforcement, vcore compile produces the index that a dependency-free Python runtime evaluates, and examples/claude-code wires it into Claude Code as a PreToolUse hook that remembers each session’s tags.

Related work

vcore follows the method of Cedar, where an authorization language is developed against a Lean model and the production engine is tested against it. Margrave and Zelkova compare access-control policies request by request; the per-request baseline above is that analysis with the session’s tags left free. vcore’s policies are a monotone kind of security automaton, and the short-counterexample argument is a small instance of the monotonicity reasoning familiar from history-based access control; the contribution is making it tight for these rules and shipping a checker proved against it. CaMeL, FIDES and Progent enforce capability, information-flow and privilege policies around LLM agents, and Invariant Labs’ toxic flow analysis looks for dangerous tool combinations. vcore is complementary to all of them: it checks what a change to a session policy does before it ships.
