What the agent may do

A coding agent in a GitHub workflow reads text anyone can write while holding a repository token. What it can do with that is decided partly by the workflow file and partly by the action that runs it. A checker proved correct in Lean decides the question for sessions of any length; we validate the model against the action's own code, and measure it across 16,346 public workflows.

Pauline BourigaultImperial College LondonSeptember 2026

An agent with standing access

A few lines of YAML give a repository an agent that answers @claude mentions, reviews pull requests, or triages issues. On a public repository the text it reads — an issue body, a comment, a pull request — can be written by anyone. The agent runs with a token for the repository and an API key, and it can read files, run commands, comment, and push.

The danger is not any single tool call. Reading a comment is fine. Reading a file is fine. Posting a comment is fine. Reading an attacker's comment, then the file that holds the token, then posting to a public comment, in one session, is not. This is Simon Willison's lethal trifecta and Meta's Rule of Two: the harm is a combination over a session, so the question has to be asked about sequences of calls, not one call at a time.

The authority envelope

For one triggering event, the agent's session has an authority envelope: the sequences of tool calls the configuration lets it make. We write it as a policy with memory — a request is permitted or not, and running it can tag the session untrusted (it read text an outsider can write) or secret (it can read a credential). Two rules then become questions about the envelope:

  • Exfiltration. Can the session reach a network egress or a public write while holding both untrusted and secret?
  • Untrusted write. Can it write to the repository after reading untrusted text?

Much of the envelope is set inside the action, not in the workflow file. We model anthropics/claude-code-action at a pinned release by reading its source: in one mode it puts the issue body and its comments into the prompt though no line of the workflow mentions them; it grants file-reading and pushing without being asked; and it writes the token into the repository's .git/config, inside the workspace the agent reads.

Verified, then checked against reality

The verdicts come from vcore, a policy checker proved correct in Lean 4 (1,462 lines, 102 theorems, no sorry). It decides refinement for sessions of every length, and a counterexample never needs more than three tool calls — a bound that is proved tight for the trifecta rule.

A verified checker is only as good as the model it is given, so we test the model by running the action's own code. An oracle executes the unmodified action against a mock GitHub API and reports what it set up — mode, tools, where the token went, and which canary-tagged texts reached the prompt. On 3,155 generated scenarios the model and the action agree on every field in 3,143; every disagreement leaves the envelope over-approximating the real run.

And the load-bearing step is not assumed. We drove the real Claude Code CLI offline, with the tag-mode configuration and a token in .git/config: it read the file and returned the token with no prompt, then posted it through the comment tool. The three-step counterexample is executable by the agent itself.

Across 16,346 workflows

We collected the public workflows that use the action and analysed the 12,414 whose agent can run. In 78% the configuration admits the exfiltration sequence, and in 66% a write to the repository after untrusted text; the token sits in .git/config in 97%. The dominant pattern is not an exotic misconfiguration — it is the default: a comment from the thread, the token in the workspace, and the comment the action maintains. Trusting text of unknown origin instead of assuming the worst barely moves the figure, because the untrusted text comes from the thread itself.

A one-line fix, verified

For a violating configuration the tool searches small workflow edits and keeps one only if the checker then proves the property holds and the change only removes behaviour. A single such edit repairs 74% of the violating configurations; most often it is one line:

# keep the token out of the agent's reach
claude_args: --disallowedTools "Read(./.git/**)"

The agent keeps every capability it uses and loses the one that reaches the credential. The fix is not advice; the same verified checker confirms it.

What it does and does not say

  • It bounds permissions, not behaviour. A counterexample means the configuration permits the sequence; whether a model would follow injected instructions to perform it is a separate question.
  • The ingredients are largely known. The prompt-injection and non-write-user risks are in the vendor's own docs; a related environment-variable exposure was reported and mitigated earlier. The contribution here is the session-level combination and its prevalence — not a new exploit. No repository is named and no exploit is released.
  • One action, one release. The method — read the framework's real behaviour, write it as a session policy, verify it, repair it — extends to other agent actions and to local coding agents. We validate it on one.
