# Evaluation

_Generated by `scripts/evaluate.py` on 2026-09-15: 13th Gen Intel(R) Core(TM) i9-13900H; Python 3.13.9;
Lean 4.34.0; 1000 random cases per experiment. Do not edit by hand._

Four questions:

1. **Proofs.** Do the theorems constrain the definitions, or could they be vacuous?
2. **Agreement.** Does the unverified code (Python runtime, Z3 checker, both parsers) agree
   with the verified Lean core?
3. **Precision.** Does checking whole sessions matter, compared with the obvious
   alternatives?
4. **Cost.** What do enforcement and checking cost as policies grow?

## 1. Proofs

The Lean development is 1462 lines with 102 theorems and no
dependency beyond Lean's standard library. It contains 0 `sorry` or `admit`.
The headline theorems use only the axioms `Classical.choice`, `Quot.sound`, `propext`
(`make axioms`).

To check that the proofs depend on the definitions, `scripts/mutate_lean.py` seeds one bug
at a time into the definitions and rebuilds. 11 of 11
mutants break the build:

| Mutant | Bug | Build fails | First declarations that fail |
|---|---|---|---|
| `forbid-ignored` | `forbid` no longer overrides `permit` | yes | `allows_iff` |
| `block-on-any-tag` | a block fires when any tag of its combination is present | yes | `blocked_iff` |
| `empty-authority-allows` | an authority with no policies allows everything | yes | `allows_iff`, `allows_nil` |
| `noncanonical-allowed` | requests with `.`, `..` or empty segments are evaluated | yes | `allows_iff` |
| `context-reset` | running a request replaces the context with its tags | yes | `step`, `mem_step` |
| `insert-drops-tag` | adding a tag to a context can lose it | yes | `mem_insert` |
| `merge-overwrites` | the compiler overwrites a table entry instead of merging | yes | `get_add` |
| `keys-off-by-one` | lookup skips the prefix equal to the whole request | yes | `covers_iff_mem_keys` |
| `fresh-segment-constant` | the junction segment is always `_` | yes | `fresh_not_mem`, `exists_rep` |
| `no-junction-reps` | representatives omit the fresh junction segment | yes | `exists_rep` |
| `search-depth-one` | the checker explores one step, the bound for single-tag rules | yes | `escalationWithin_sound`, `escalationWithin_eq_none` |

This shows the proofs are not vacuous; it does not show the definitions say what you want.
The first declaration to fail is often a lemma that restates a definition (`allows_iff`),
and Lean then stops checking the theorems built on it. Whether the semantics is the
intended one is what the contract theorems in `Policy.lean` are for: they state the rules
of the language (`forbid_denies`, `block_denies`, `allows_canonical`, ...) in a few lines
each, for a reviewer to read.

## 2. Agreement

Random authorities come from two families (see `python/tests/generate.py`): arbitrary
patterns over an adversarial segment alphabet with combination rules of one to three tags,
and small tool/resource policies where most behaviour is in labels and combinations.
30% are two-policy authorities. Request sequences include non-canonical requests. The
parser experiment uses documents that are broken in one place 85% of the time.

| Comparison | Cases | Disagreements |
|---|---|---|
| Python runtime (Lean-compiled index) vs Lean source semantics, sequences of 1 to 6 requests | 1000 | 0 |
| Z3 checker (searching 2 requests deeper than the bound) vs Lean checker: verdict, both witnesses replayed through Lean, witness length | 1000 | 0 |
| Python parser vs Lean parser: accept or reject, and the statements read | 2000 | 0 |

**Seeded bugs in the unverified code.** Each bug is patched into the Python runtime or the
Z3 checker, and the differential harness runs until it disagrees with Lean.
9 of 10 are caught by random testing:

| Mutant | Bug | Random cases until caught (of 1000) |
|---|---|---|
| `forbid_ignored` | `forbid` does not override `permit` | 1 |
| `block_on_any_tag` | A block fires when any tag of its combination is present, not all | 25 |
| `chain_any` | An authority allows a request if any of its policies does | 1 |
| `denied_request_taints` | A denied request still adds its tags | 4 |
| `noncanonical_allowed` | Requests with empty, `.` or `..` segments are evaluated instead of denied | 1 |
| `keys_off_by_one` | `a/b/**` is not looked up for the request `a/b` itself | 11 |
| `suffix_as_prefix` | Suffix entries are looked up under prefixes | 2 |
| `character_glob` | `secrets/**` also covers `secrets-public`: prefix matching on the joined string | 66 |
| `checker_depth_two` | The checker searches two requests deep, the bound for single-tag rules | 82 |
| `no_fresh_segment` | The Z3 encoding only considers segments that appear in the policies | **not caught** |

`no_fresh_segment` is a real completeness bug: it misses escalations that go through a path segment neither policy names, and random policies almost always name enough segments to hide it. `test_fresh_segment_needed` exposes it with a three-line policy pair, and its Lean counterpart (`no-junction-reps`) breaks the proof of `exists_rep`. Testing finds the common bugs quickly; the proof closes the rare ones.

## 3. Precision

On the same 1000 policy pairs (the new policy is a small edit of the old one 60% of the
time, otherwise independent), 598 are refinements and 402
are not. Counterexample lengths by the width of the old policy (its largest combination):

| Width | Pairs | Refinements | 1 request | 2 requests | 3 requests | 4 requests |
|---|---|---|---|---|---|---|
| 0 | 92 | 60 | 32 | 0 | 0 | 0 |
| 1 | 116 | 72 | 36 | 8 | 0 | 0 |
| 2 | 386 | 217 | 134 | 25 | 10 | 0 |
| 3 | 406 | 249 | 124 | 24 | 8 | 1 |

No counterexample is longer than width + 1, as `short_counterexample` requires; the bound is reached at widths 0, 1, 2, 3. 19 of the 402 counterexamples need more than two
requests.

Two obvious alternatives, on the same pairs:

| Alternative | Escalations missed | Refinements reported as escalations |
|---|---|---|
| Per-request diff with the session's tags left free (what analyzers for stateless policy languages check) | 29 of 402 (7.2%) | 94 of 598 (15.7%) |
| Bounded search over sessions of two requests | 19 of 402 (4.7%) | 0 (sound) |

The per-request diff misses changes that only act across requests, such as removing a
label, which changes no single decision. It raises false alarms for changes that only
matter in combinations of tags no session can reach. A bounded search is sound but needs to
know how deep to go; `short_counterexample` supplies that depth.

## 4. Cost

**Enforcement.** Synthetic policies of `n` statements; 2000 requests each, decided by the
Python runtime.

| Statements | Compile (Lean, incl. JSON) | Decision, compiled index | Decision, scanning statements |
|---|---|---|---|
| 10 | 0.1 ms | 6.0 µs | 2.3 µs |
| 100 | 0.6 ms | 5.8 µs | 19.6 µs |
| 1000 | 26 ms | 4.2 µs | 162.3 µs |
| 10000 | 2.2 s | 12.8 µs | 1738.5 µs |

A decision on the compiled index costs `2|x| + 3` lookups for a request of `|x|` segments,
whatever the size of the policy, which is what `compile_correct` licenses. Compilation is
quadratic in the number of distinct patterns (the Lean table is an association list).

**Refinement checking.** Median of 3 pairs per size; the new policy drops one label. Z3 has
a 10 s timeout per query with the string encoding.

| Statements | Lean checker | Z3, segment encoding | Z3, string encoding |
|---|---|---|---|
| 16 | 0.8 ms | 46 ms | 26 ms |
| 64 | 3.7 ms | 253 ms | 396 ms (1 of 3 timed out) |
| 256 | 194 ms | 945 ms | not run |
| 1024 | 14.4 s | 2.4 s | not run |

The verified checker computes what every policy says about every representative request;
there are roughly (distinct prefix patterns) × (distinct suffix patterns) of them, so its
cost grows faster than Z3's. It is interactive up to a few hundred statements, which covers
agent policies written by hand. The Z3 encoding by segments, which builds in the same
finite-alphabet idea, scales better; the natural string encoding does not.

## Threats to validity

* Random policies are synthetic, and the precision figures depend on how they are drawn.
  The case study is small and hand-written; policies from deployed agents would be better
  evidence.
* The Lean and Z3 checkers were written by the same author. They share no code and use
  different encodings, but a shared misreading of the semantics would not show up as a
  disagreement. The contract theorems are the defence.
* Timings are single-machine medians over few samples.
